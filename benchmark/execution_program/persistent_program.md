# Persistent typed execution across lifecycle refresh

**Keep bounded graph + typed output preparation as the performance candidate.**
The new persistent typed backend passes the small preservation gates, including
actual newborn execution, but is slower overall in these short screens. It
remains an opt-in scientific-program experiment. Production `src/`, the default
executor and the three existing preparation modules are unchanged.

## What the prototype does

The existing Shared/Tight/DirectPlanConstruction backend can now readmit eligible
regions after same-schema organ birth and removal. It retires old owners before
logical refresh, uses ordinary refresh as the bookkeeping oracle, and lowers
current eligible regions again. An unaffected region keeps its wrapper and
scientific columns while metadata headers and Tight frames are rebound. Reuse
checks actual targets, references, models, calls, environment handles and streams.
Public exposure permanently keeps the application ordinary for that timeline.
Unsupported protocols keep ordinary execution; profiling retains the whole
ordinary plan. No scientific equation or existing `noinline` child boundary changes.

Early preservation gates found two real cold-protocol defects. Descendants that
had not run were initially synthesized with their parent's time/publication;
subsequently, cold reconstruction lost pending runtime-change synchronization
for an unentered child. The final prototype records per-node invocation and
per-edge lookup metadata separately and retains exact cold header references.
It preserves skipped children, model-only lookups and delayed ordinary entry.
Root-owner seeding uses one identity index per pass instead of quadratic scans.
Declaration admission uses strict type/effect inference without evaluating live
declarations speculatively.

The six XP model families are explicitly audited using existing private-context
capabilities, inspected-source hashes and concrete pilot numeric types. Ports,
selectors, coupling, clocks and ownership still come from PSE declarations.
Growth, pruning and unsupported public-context/distributed/temporal boundaries
continue through ordinary execution. This is not automatic effect inference for
arbitrary context-unused Julia code or an optimization tied to leaf identity.

## Small warm screens

Each screen has two balanced forward/reverse cycles, one fresh independent
scientific scene per sample, identical ordinary A/A labels and four policies:
ordinary, improved preparation only, persistent typed only, combined. Construction,
normal logical preparation, additional typed installation, execution and their
complete sum are separate. The deliberately prebuilt ordinary plan, declaration proof queries,
owner materialization, ordinary refresh, re-lowering and metadata work are charged.
Common definition loading, registration, source-hash verification and monitoring
are outside the warm phase clocks. XP weather CSV IO is inside construction here; this differs from the prior scaling
cohort, so do not pool their times or add percentage gains.

PB uses 16 objects × 8 steps; XP uses four accelerated days, one original palm,
8→20 actual objects, architecture=false and phyllochron speeds 0.2. Final typed XP
coverage records 32 selected batch entries, four refreshes, eight reused regions,
24 readmissions and 32 captured regions. Growth and 124 ordinary batch invocations
still use ordinary execution. Neither tested workload increases model width.

## Next candidates and limits

The evidence argues for keeping preparation-only and avoiding default promotion
of this typed backend. Before larger typed runs, test these specific hypotheses:

1. Reuse strict declaration type/effect proofs by current Julia world and model/
   spec type, rather than repeating compiler queries for each independent model.
   Cache proof metadata only, with bounded invalidation; never declaration values.
2. Retain/reuse the ordinary cold owners already created during preparation and
   refresh. Apply recorded epochs only when exposure/capture needs them, preserving
   pending headers and call-site ownership. This could remove Shared-owner
   reconstruction, at the cost of ordinary owner memory; measure that tradeoff.
3. For proven same-schema append/remove deltas, update only affected memberships
   and rows instead of rebuilding the full changed application's numeric columns.
   Keep complete fallback when the proof fails. Test it alone and with owner reuse.

These are unimplemented hypotheses, not promised gains. The persistent program is
useful as a semantics-checked foundation for those experiments. Current limits
include fresh Tight-frame allocation during rebasing, whole-owner capture, cold
header memory, installation before public inspection of the ordinary zero-step
plan, and the need for a live scheduled sentinel to readmit targetless apps. A
completely empty initial plan retains ordinary behavior after external additions.
Further qualification should include sampling-error metadata and wider schema/
model populations before production adoption. Million-organ scaling, mature
architectural palms and a new cold matrix are deliberately not run for a candidate
that loses these cheap checks.

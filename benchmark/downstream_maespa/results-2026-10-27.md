# MAESPA performance evidence — 27 October 2026

The final adjacent comparison reduces the unchanged scenario's continuation time by **12.7% without history** and **12.3% with all history**, relative to the pinned parent. Allocations fall by **13.9%** and **13.2%** respectively. This measures the existing MAESPA calls; MAESPA has not yet adopted `evaluate_call!`/`accept_call!`.

## Workload and method

MAESPA `a308f4b3531274f48f43644d485ea73241886f6d`; unchanged `examples/two_species.jl`: two species/trees, one soil layer, 16 logical leaf units, 100 applications, 27 objects, 96 half-hour steps. Canopy-air iteration is disabled in this example. Native leaf energy/photosynthesis, crown radiation, canopy aggregation and soil calculations execute. This does not cover Tuzet, PlantBiophysics, understorey, file I/O or a larger scene.

Julia 1.13.1, `apple-m3`, 14 compute and 14 GC threads. Separate Kaimon processes use pinned matching dependency versions. Five warmed samples per output mode; the final parent run immediately precedes the candidate. No other task-owned tests/profilers run during these timings. Ambient desktop load remains uncontrolled. Repeated continuation samples report zero compilation/recompilation time. Package import, process startup and cold compilation are excluded; allocations are cumulative bytes, not RSS.

## Acceptance mechanism and its overhead

Deterministic overwrite-only counter fixture, one fixed timestep, `outputs=:none`, five samples of 10,000 operations; a separate eight-step simulation compares complete final states and retained rows. Each operation includes result traversal on both paths, so these are not bare kernel timings.

| Engine | Targets | Path | Median µs/op | Bytes/op |
| --- | ---: | --- | ---: | ---: |
| Parent | 1 | replay | 1.669 | 1840.0 |
| Parent | 16 | replay | 18.425 | 26800.2 |
| Candidate | 1 | replay | 1.712 | 1840.0 |
| Candidate | 1 | accept | 1.897 | 1824.0 |
| Candidate | 16 | replay | 19.335 | 26800.5 |
| Candidate | 16 | accept | 19.565 | 26784.2 |

Acceptance executes **one child kernel instead of two**, with identical retained rows and states in this fixture. Its trivial child only adds a scalar; validation/staging therefore costs more wall time than the eliminated tiny kernel. This does **not** establish a MAESPA end-to-end gain from replay removal. Measure that migration with the actual solvers and scientific regressions before adopting it broadly. Ordinary replay is 2.6%/4.9% slower for one/16 targets in the final adjacent run, with unchanged allocation counts. The execution guards add work to very small calls; the full-scenario gain is not a universal framework-wide speedup.

The first implementation exposed a real preparation bug: `empty!(IdDict)` allocated a new 288-byte table at both evaluation and acceptance. The final implementation reuses `Dict` storage, keeps revision values unboxed, keeps the private TLS slot prepared, and reads evaluation state once per bulk call. The warmed public API allocation regression excludes result-view traversal and prevents this fixed per-iteration buffer allocation from returning. Separate shared-row tests verify both leaves receive the same mutable environment object, see in-place updates without lifecycle refresh, and sample it with zero warmed allocations.

## Remaining bottlenecks and next measurements

An eight-run post-timing CPU profile selects 1008 continuation stacks. Nearest-package attribution is PlantSimEngine 50.3%, MAESPA 45.7%, GC 3.8% and PlantMeteo 0.2%; no compiler samples are selected. This is stack attribution, not a causal separation of independent scientific/framework time.

- PSE `Status` reads/writes account for 30.0% of selected stacks. Investigate prepared or unrolled trial-input updates at the MAESPA/PSE boundary; confirm the dynamic symbol lookups before adding another interface.
- MAESPA `_set_leaf_trial_inputs!` accounts for 13.0% and `_validate_canopy_atmosphere` for 9.3% as the nearest package sites. Next compare a prepared whole-row backend specialization that validates once per state update and narrower trial-state updates; retain domain checks at the appropriate boundary.
- PSE `_materialize_call` accounts for 5.5%. Use singular/bulk paths that avoid materialized target views when inspecting only one model or aggregating known columns. Benchmark existing accessors before expanding the API.
- Pilot replay removal at an actual expensive MAESPA coupling boundary, preserving the evaluated current state and handling earlier best candidates explicitly. The tiny fixture shows why kernel-count reduction alone is insufficient performance evidence.

The original registered-release profile attributed 71.0% to PSE, 22.4% to MAESPA and 6.6% to GC. That difference includes changes already in the parent; percentages from separate profiles are not absolute speedup estimates.

## Validation and reproduction

All 61 test files passed (8,176 assertions), plus 11 Aqua checks, docstring doctests and three new documentation example blocks. Twelve affected files were rerun after the bulk/storage changes; the allocation/acceptance file was rerun after the last compiler hint. The single monolithic suite attempt exceeded Kaimon's gate timeout, so completed files were run/recorded in bounded batches. Local evidence is separate from hosted CI.
